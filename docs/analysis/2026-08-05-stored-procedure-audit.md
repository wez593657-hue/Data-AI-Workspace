# 五类重点经营存储过程全面审查报告

审查日期：2026-08-05  
审查对象：到期承接、新客经营、潜力提升、流失挽回、睡眠户唤醒的 10 个明细/统计存储过程。  
审查方式：静态代码、模板、需求记忆卡片、目标/临时表 DDL 和仓库校验；未连接 Kingbase，未执行真实执行计划或生产样本回放。

## 1. 结论

当前过程具备统一的 Oracle 兼容过程骨架：全部包含 `V_SYSDAT` 格式校验、`OUTCDE`、`WHEN OTHERS`、`ROLLBACK`、分段 `COMMIT` 和 `SYS_PRC_STEP_LOGS`。日期参数静态校验通过。

但不宜判定为“严格符合模板且可直接上线”：发现 1 项 P0 业务错误、5 项 P1 数据正确性或性能风险，以及一组模板可观测性和事务一致性差异。最先应修复睡眠户唤醒判定，再统一机构粒度，并完成索引、回放和数据库编译验证。

| 风险 | 数量 | 结论 |
|---|---:|---|
| P0 | 1 | 睡眠户唤醒可被错误标记，直接污染明细、客户数和唤醒率 |
| P1 | 5 | 机构串数、历史扫描、事务原子性和索引缺口会影响正确性或批处理稳定性 |
| P2 | 4 | 模板步骤、日志和异常分类不完整，降低可运维性 |
| 已确认可合并/废弃步骤 | 3 | 见第 5 节；未将必要的双周期计算或阻断校验误判为冗余 |

1. 模板要求过程开始、参数检查、关键处理量和过程结束可追溯；当前主要记录步骤完成和异常，未记录显式开始日志、入参和受影响行数。

## 4. 业务、数据与性能问题

### P0-SLEEP-001：唤醒状态的判定不符合已登记口径

- 位置：`PRC_ADS_CUST_SLEEP_WAKE_DTL.sql:126-144, 156-165, 325-346`。
- 现状：`TMP_ADS_SLEEP_WAKE_PROD` 仅归集当月拥有定期、理财或保险账户的客户；`IS_WAKE` 只判断该表是否存在；后续直接把 `IS_WAKE=1` 写为 `WAKE_STATE='1'`。
- 规则冲突：`tmp_pro_ads_cust_sleep_wake_dtl.ddl:61` 明确 `IS_WAKE` 为“基线产品余额=0 且当日>0”，基线日为 `V_WAKE_BASELINE_DATE`。
- 影响：已有产品账户、但本月余额未从 0 增加的客户会被误判唤醒；统计过程据此计算 `WAKE_CUST_CNT/WAKE_RATE`，导致统计同步失真。
- 推荐修复：删除账户存在性作为唤醒依据，按 `(PERSN_LEGAL_BK_CODE, CUST_ID, ORG_ID)` 比较基线和当日定期/理财/保险余额；任一产品满足“基线=0 且当日>0”时置 1。补充“已有账户余额不变”“从正数增至正数”“基线缺失”“跨机构同客户”回放用例。

### P1-ORG-001：机构维度关联不完整

| 位置 | 问题 | 风险与修复 |
|---|---|---|
| 潜力明细 `:160-177` | `DWD_CUST_MAN`、当前月日均资产、时点资产均未显式按 `ORG_ID` 关联 | 同法人行同客户多机构时可能放大行数或串值；统一以客户、法人行、机构三键关联，或用 `ROW_NUMBER` 固化唯一管户记录。 |
| 流失明细 `:175-181` | 本月/上上月资产的 `FULL JOIN` 和管户关联缺少 `ORG_ID` | 轻/重度流失客户可能跨机构配对；在两侧资产源、当前时点余额和管户关系中补齐机构键。 |
| 新客明细 `:280-283` | `DWD_CUST_MAN` 关联未限定机构 | 多管户记录可能使新客明细重复；按机构限定或先去重管户关系。 |
| 潜力统计 `:112-120, 129-131` | 月日均达标预计算表与明细关联未使用 `ORG_ID` | 多机构下可将一个机构的达标状态带入另一机构统计。 |
| 睡眠明细 `:122-165, 299-306` | 主动动账、产品临时表只存客户+法人行，`EXISTS/NOT EXISTS` 不能区分机构 | 可跨机构排除睡眠候选或跨机构标记唤醒；临时表和关联键均加入 `ORG_ID`。 |

说明：历史材料曾记录“潜力提升同法人行下 ORG_ID 为 1:1”的业务约束。该约束尚未在过程或 DDL 中显式强制，故本项定级为需样本验证的 P1 风险，而非断言当前必然产生错误。

### P1-PERF-001：统计过程的机构层级起点扫描全历史明细

- 位置：潜力统计 `:111-116`、流失统计 `:123-128`；新客统计同类机构树展开；旧版睡眠过程已有此问题，当前睡眠统计 `:75-79` 已按当日过滤。
- 现状：`START WITH` 的机构集合部分过程只按 `ORG_ID IS NOT NULL`，未限制 `DATA_DATE=V_SYSDAT/V_DATA_DATE`，但后续统计又只使用当日明细。
- 影响：历史不断增长时，递归起点、`DISTINCT` 和层级展开持续放大，通常不改变当日结果但增加 I/O、排序和临时空间。
- 推荐修复：先生成当日 `DISTINCT ORG_ID` 临时集合，机构树仅从该集合展开；该集合可同时为机构分支统计复用。

### P1-TXN-001：过程级失败不能恢复已提交结果

- 位置：全部 10 个过程的分段 `COMMIT` 与末尾 `WHEN OTHERS ... ROLLBACK`。
- 影响：第 N 段失败时，前 N-1 段的目标表删除、阶段表或结果已提交。再次运行可否完全修复依赖每个过程的清理范围；到期承接的跨周期冻结尤其需要验证幂等性。
- 推荐方案：保留临时表阶段提交的模板约束，但将最终 ADS 目标表删除、MERGE/INSERT 和验证置于同一可回滚事务；或采用批次号/影子表，验证通过后原子切换。必须补充中途异常注入与重跑回归。

### P1-INDEX-001：目标表和临时表 DDL 未声明主键或索引

- 证据：目标/临时 DDL 中未检出 `PRIMARY KEY`、`UNIQUE` 或 `CREATE INDEX`。
- 影响：按 `DATA_DATE` 删除、三键关联、统计 `GROUP BY`、`EXISTS` 和历史保留删除可能退化为全表扫描；缺少唯一性约束也无法防止重复写入。
- 推荐索引：明细表优先 `(DATA_DATE, PERSN_LEGAL_BK_CODE, CUST_ID, ORG_ID)`；统计表优先 `(DATA_DATE, PERSN_LEGAL_BK_CODE, STATIS_OBJ, STATIS_CYCLE[, STATIS_TYP/LVL_CHURN/LVL_CRIT])`；每个物理临时表按其 `TRUNCATE` 后的关联键建立必要索引。最终顺序须以 Kingbase 的 `EXPLAIN ANALYZE` 和数据分布确定。

### P1-DEADLINE-001：到期承接双周期实现复杂且存在回归压力

- 位置：明细 `:767-1139`、统计对应的 C/P 阶段。
- 结论：当前期和上期计算虽高度相似，但分别使用不同 `DATA_DATE` 与冻结更新规则，不能直接删除任一段。风险在于复制逻辑的后续修复易只改一侧。
- 推荐优化：将共同的源集和金额计算先物化为参数化阶段表，当前/上期只保留日期窗口和写入策略差异；采用同一组回归样例断言两期字段域和行数。不要在未回放前做大规模抽象。

### P2-OBS-001：缺少处理量和关键口径可观测性

- 位置：所有过程的 `SYS_PRC_STEP_LOGS` 调用。
- 推荐：日志消息增加删除行数、临时表写入行数、目标表新增/更新行数、零分母数、机构树展开行数和校验失败明细。异常日志同时记录 SQLCODE/SQLSTATE（若兼容模式支持）及步骤名。

### P2-DATE-001：日期规范已通过，但仍需防回归

`validate_procedure_date_parameters.py` 通过。所有新增日期口径仍必须在 `sys_fun_deal_date`、日期规则和对应记忆卡片三处同步登记；禁止将 `TO_DATE(V_SYSDAT)`、日期加减直接用于推导业务边界。

## 6. 建议实施顺序与验收

1. 修复 P0-SLEEP-001，并以基线/当日余额构造正反例回放；同时补齐睡眠临时表 `ORG_ID` 粒度。
2. 对潜力、流失、新客的机构关联执行重复行和跨机构比对；确认业务约束后补齐键或显式去重规则。
3. 将统计过程机构树收敛到当日机构集合，合并睡眠 `TMP8` 更新，清理确认后的死表。
4. 设计并执行索引：先采集表行数、基数、现有索引和 `EXPLAIN ANALYZE`，再发布 DDL；不得仅凭静态代码决定索引顺序。
5. 调整日志和事务边界，完成异常注入、幂等重跑、月初/月末、跨季/跨年、零客户、无管户、同客户多机构的回归。
6. 在 Kingbase 目标版本完成编译、样本回放、执行计划和锁等待验证后，再给出上线结论。
