# 16 执行规则

## 16.1 核心原则

所有操作必须严格遵循"用户命令驱动"原则，禁止擅自执行任何变更。

### 16.1.1 禁止自动执行的操作

| 操作类型 | 禁止行为 | 正确做法 |
|----------|----------|----------|
| 代码生成 | 自动生成存储过程、ETL脚本、DDL等 | 等待用户明确命令 |
| 文件修改 | 擅自修改数据资产（DDL、字典、Mapping） | 等待用户明确命令 |
| 数据清理 | 自动删除文件或目录 | 等待用户明确命令 |
| 提交推送 | 自动执行git commit/push | 等待用户明确命令 |
| 校验修复 | 自动执行ai_repair_loop修复 | 等待用户明确命令 |

### 16.1.2 允许自动执行的操作

| 操作类型 | 允许行为 | 说明 |
|----------|----------|------|
| 校验检查 | 执行workspace_validation.py | 仅检查，不修改 |
| 状态查询 | git status, git log | 只读操作 |
| 项目分析 | 查看目录结构、文件内容 | 只读操作 |
| 规则检查 | 检查是否符合规范 | 仅检查，不修改 |

## 16.2 执行流程

### 16.2.1 修改流程

```
用户命令 → 分析需求 → 确认方案 → 执行操作 → 验证结果 → 等待确认
     │            │           │           │           │
     ▼            ▼           ▼           ▼           ▼
  明确意图     理解范围    用户确认    执行修改    验证输出
```

### 16.2.2 数据开发流程

```
用户提供需求文档
        │
        ▼
检索记忆卡片（requirements/{需求名称}规则记忆卡片.md）
        │
        ├── 存在记忆卡片
        │       │
        │       ├── 版本一致 → 继续开发
        │       │
        │       └── 版本不一致 → 列出差异点 → 用户确认 → 更新记忆卡片/需求文档
        │
        └── 不存在记忆卡片 → 在需求确认阶段创建
        │
        ▼
用户命令生成DDL
        │
        ▼
用户命令生成数据字典
        │
        ▼
用户命令生成Mapping
        │
        ▼
用户命令生成存储过程
        │
        ▼
更新记忆卡片（记录版本、代码映射、规则说明）
```

### 16.2.2.2 两类开发流程路由

项目开发统一分为以下两类：

| 流程类型 | 触发语义 | Harness profile |
|----------|----------|-----------------|
| 需求开发 | 需求文档、业务规则、生成或修改存储过程 | `requirement_development` |
| 表结构变更 | Mapping Excel 变更、MD/DD/数据字典与 Excel 对齐 | `schema_change` |

用户命令同时包含两类目标时，先执行需求开发，再执行表结构变更。仅分析、查询或校验不进入修改流程。无法唯一判断时必须暂停并请求用户确认。

需求开发必须依次完成：需求与记忆卡片分析、范围确认、项目扫描、目标表/源表识别、源表能力分析、字段可实现性确认、材料补充循环、需求审核、记忆卡片更新、存储过程开发、存储过程审核、临时表生成、完整校验、用户确认、提交、推送。

表结构变更必须依次完成：分析 Mapping Excel 最近变更、扫描 MD/DD/数据字典、输出修改范围、用户确认、修改资产、一致性审核、完整校验、用户确认、提交、推送。

审核失败必须记录结构化审核证据并退回指定阶段，不得跳过或直接进入提交。审核 agent 可以由当前任务按角色隔离执行，也可以启动独立只读 Codex 子任务；独立子任务不得创建或切换 Git 分支。

### 16.2.2.1 记忆卡片版本控制规则

| 规则项 | 要求 |
|--------|------|
| 命名规范 | `{需求名称}规则记忆卡片.md`，存放在`requirements/`目录下 |
| 版本同步 | 每次需求变更时，必须同步更新记忆卡片版本，并记录变更内容 |
| 版本比对 | 开始开发前必须比对记忆卡片版本与需求文档版本，不一致时需列出差异点 |
| 用户确认 | 版本差异必须获得用户确认后才能继续开发 |
| 内容要求 | 必须包含：版本历史、需求变更流程、需求-代码映射、功能概述、数据来源、指标定义、统计维度、存储过程信息、清理规则、待确认事项、权限说明 |

### 16.2.3 任务完成与验收流程

对包含多个文件、过程、阶段或校验项的任务，必须遵循以下规则：

1. 开始执行前记录完整验收清单，明确所有待修改对象、校验项和完成条件。
2. 每完成一个过程或阶段，只向用户报告进度和已验证结果，不得给出结束性结论。
3. 持续执行后续过程、阶段和校验，直到验收清单中的全部事项完成。
4. 仅在全部任务和校验完成后，才能回复任务完成。
5. 如遇无法自行解决的真实阻塞，必须说明阻塞事实、影响范围和所需用户决策；不得将阶段性完成、复杂度、上下文长度或等待时间视为结束条件。

### 16.2.4 强制任务清单

每个包含多个文件、过程、阶段或校验项的任务，必须使用
`templates/task_execution_checklist.md` 创建任务执行清单。任务清单不是参考材料，
而是任务的强制状态记录。未创建任务清单，不得进入开发、生成、修改或修复阶段。

任务清单必须在任务开始时建立，并至少包含以下阶段：

1. 检查当前分支、工作区和远程同步状态。
2. 明确需求范围、验收标准、待修改对象和禁止修改对象。
3. 按先后顺序记录需求、规范、模板、数据字典、Mapping、DDL 和现有实现的读取结果。
4. 输出实现方案、文件清单、影响范围和风险，并等待用户确认。
5. 按项目规定执行开发或生成操作。
6. 执行快速校验和完整校验，记录命令及结果。
7. 完成全部验收项后，汇报变更和验证结果，并等待用户明确提交或推送命令。

每个清单项必须记录状态、实际证据和完成条件。状态只能使用：
`待处理`、`进行中`、`已完成`、`已阻塞`、`已恢复`。不得仅通过口头说明或批量标记为完成。

### 16.2.5 阶段门禁与强制停止

下列条件任一不满足时，必须停止当前任务，不得进入下一阶段：

- 未创建任务执行清单；
- 工作区已有变更但尚未完成归属和影响确认；
- 需求、字段来源、业务规则或验收标准不明确；
- 实现方案或修改范围尚未获得用户确认；
- 必要文件读取不完整或读取顺序无法追溯；
- 快速校验或完整校验失败；
- 验收清单仍有未完成项；
- 用户未明确授权提交、推送或合并。

强制停止不得只记录“已停止”或“无法继续”。必须在任务清单中记录以下内容：

| 必填项 | 要求 |
|--------|------|
| 停止原因 | 具体说明为什么不能继续 |
| 原因分类 | 需求不清、文件冲突、工作区风险、校验失败、权限不足或外部依赖等 |
| 证据 | 文件路径、命令、错误信息、校验输出或其他可复核信息 |
| 影响范围 | 说明影响的阶段、文件、数据对象或业务结果 |
| 推荐处理方案 | 给出优先方案和选择理由 |
| 备选方案 | 说明其他方案及适用条件和风险 |
| 需要用户决定的事项 | 明确用户需要补充或确认的内容 |
| 恢复条件 | 说明满足什么条件后才能继续 |
| 当前状态 | 使用`已阻塞`或`等待用户确认`，恢复后改为`已恢复` |

在阻塞状态下，只能执行与定位、取证和验证恢复条件有关的只读操作，不能擅自修改、删除、生成、提交或推送。收到用户决策后，必须先将决策和恢复条件写入清单，再重新检查恢复条件，确认满足后才能继续。

## 16.3 操作规范

### 16.3.1 修改前确认

所有修改操作前必须：
1. 明确告知用户即将执行的操作内容
2. 说明影响范围和潜在风险
3. 等待用户确认后再执行

### 16.3.2 修改后验证

所有修改操作后必须：
1. 执行相应的校验脚本验证修改正确性
2. 提供修改结果摘要
3. 等待用户确认后再提交

### 16.3.3 提交规范

提交前必须：
1. 执行完整工作区校验（workspace_validation.py full）
2. 确认所有校验通过
3. 等待用户明确命令后执行git commit/push

### 16.3.4 清单执行证据

任务执行清单必须与任务同步更新，不得在任务结束时补写。每个已完成阶段至少记录：

- 实际读取或修改的文件路径；
- 实际执行的命令或校验脚本；
- 命令结果和失败信息；
- 对应验收标准的验证结论。

助手不得仅输出“将按流程执行”的承诺。缺少任务清单、阶段证据或用户确认时，必须按16.2.5节处理为阻塞，不得声明该阶段完成或任务完成。

## 16.3.5 目标任务白名单

涉及数据资产的任务，执行修改前必须建立并经用户确认 `change_manifest.yaml`，至少列出任务目标、需求依据、允许修改的文件路径和目标表、字段级修改原因、预期结果、验收命令，以及仅仅读取的上游文件。

执行器只能修改清单中的文件和目标表。上游文件即使被下游过程读取，也只能读取和取证，不得因被引用而修改。需求文档或现有存储过程没有明确证据的源表、源字段、别名、中文名和转换规则必须保持为空并记录原因，禁止猜测补齐。Excel 到 Markdown 同步也必须限定在清单目标表，禁止重写非目标表。

## 16.4 权限边界

| 权限级别 | 允许操作 | 禁止操作 |
|----------|----------|----------|
| 只读权限 | 查看、分析、校验 | 修改、删除、生成 |
| 修改权限 | 按用户命令修改指定文件 | 修改未授权文件 |
| 提交权限 | 按用户命令提交 | 擅自提交 |

## 16.5 违规处理

| 违规类型 | 处理方式 |
|----------|----------|
| 擅自生成代码 | 立即停止，删除生成内容，向用户道歉 |
| 擅自修改数据资产 | 立即停止，恢复原始状态，向用户道歉 |
| 擅自提交推送 | 立即撤销，恢复原始状态，向用户道歉 |

## 16.7 错误案例库

> 本节记录真实开发过程中出现的各类错误。每条案例包含：错误分类、触发场景、具体表现、根因分析、改进措施。
> 定期回顾本节内容，确保同类错误不重复出现。

### 案例#001 | 类别: 流程违规 — 绕过门禁直接开发

| 项目 | 内容 |
|------|------|
| **发生版本** | 对私客户标签表 v1.3.0、睡眠户唤醒 v2.5.0 |
| **错误场景** | 用户下达开发命令后，直接编写存储过程代码，未调用 crm-requirement-development Skill |
| **具体表现** | Skill 管理的流程步骤（需求解读→版本管理→质检→审批→harness证据）全部被跳过，代码无审计追溯 |
| **根因** | 开发者将"用户命令"理解为"立即写代码"，忽略了 Must-Invoke Gate 要求 |
| **改进措施** | 任何存储过程开发/修改的**第一步**必须调用 Skill。禁止在 Skill 加载前写入任何代码文件 |
| **关联规则** | project_memory.md — Must-Invoke Gate |

### 案例#002 | 类别: 流程违规 — DDL字段变更未经用户确认

| 项目 | 内容 |
|------|------|
| **发生版本** | 对私客户标签表 DATA_DATE 字段；睡眠户唤醒 v2.6.0 SLEEP_TYP/WAKE_DATE/CARRYOVER/NEW 字段 |
| **错误场景** | 因业务需要，在目标表 DDL 中直接新增字段，未经用户逐一确认 |
| **具体表现** | 字段变更禁令被违反：用户发现 DDL 中出现了未经审批的新字段 |
| **根因** | 开发者认为"逻辑需要这个字段"等同于"用户批准了这个字段" |
| **改进措施** | DDL 字段新增/删除/重命名**必须**列出变更清单（字段名+类型+用途+必要性），由用户逐项确认后方可执行。即使字段在其他表中已存在也不例外 |
| **关联规则** | project_memory.md — Field Change Prohibition |

### 案例#003 | 类别: 设计缺陷 — 同源快照导致唤醒判定失效

| 项目 | 内容 |
|------|------|
| **发生版本** | 睡眠户唤醒 v2.5.0 |
| **错误场景** | 睡眠判定和唤醒判定使用同一个 DWS_CUST_ASSE_LIAB 快照（DATA_DATE=V_DATA_DATE, BAL_TYPE='1'） |
| **具体表现** | AUM<100 的客户只要持有任何产品余额，就同时满足"睡眠"和"已唤醒"两个互斥状态。唤醒率 = 持有产品的睡眠客户占比，而非经营效果 |
| **根因** | "持有产品"用绝对值判定，未采用时间维度的增量对比 |
| **改进措施** | 唤醒判定改为**双快照增量对比**：基线快照产品余额=0 AND 当日快照产品余额>0 → 才视为新增持有。在编写任何"变化量"/"新增"类指标前，必须先回答"变化前的基线是什么" |
| **关联规则** | 睡眠户唤醒规则记忆卡片 v2.6.0 |

### 案例#004 | 类别: 边界漏洞 — 月首日唤醒基线取当日数据

| 项目 | 内容 |
|------|------|
| **发生版本** | 睡眠户唤醒 v2.6.1 |
| **错误场景** | 月首日：V_CURR_MONTH_BEGIN = V_DATA_DATE（同一天）。唤醒基线 mb.DATA_DATE = V_CURR_MONTH_BEGIN，当日快照 a.DATA_DATE = V_DATA_DATE，两者指向同一份数据 |
| **具体表现** | 月首日所有客户的唤醒条件 `mb.FIN=0 AND a.FIN>0` 永远不成立（同一数据源），上月睡眠当日买产品的客户漏识别 |
| **根因** | 未考虑"日期参数取同一天"的边界情况。设计时仅按"月初是变化起点"的直觉选用了 V_CURR_MONTH_BEGIN |
| **改进措施** | 日期相关的对比逻辑必须检查"两个日期是否可能相等"。月首日特殊处理：唤醒基线取 V_PREV_DAY（上月末真实状态） |
| **检测方法** | 设计阶段对所有日期变量做相等性测试：`IF DATE_A = DATE_B THEN 是否有替代方案？` |
| **关联规则** | 睡眠户唤醒 v2.6.2 |

### 案例#005 | 类别: 设计缺陷 — 月首日丢弃上月末存量

| 项目 | 内容 |
|------|------|
| **发生版本** | 睡眠户唤醒 v2.8.0 |
| **错误场景** | 月首日步骤[A]跳过（不读昨日DTL），TMP_BASE 为空，步骤[B]仅从当日快照筛选 AUM<100 的候选 |
| **具体表现** | 上月睡眠但当日 AUM≥100 的客户从清单中消失（如上月 AUM=50、当日购买理财后 AUM=120） |
| **根因** | 将"月度重置"误解为"每月从零重建"，忽略了用户明确给出的公式：`月度总量 = 上月末存量 + 当月新增`。公式中的"上月末存量"本身就是基数 |
| **改进措施** | 任何涉及"重置"/"重新计算"的设计，必须先对照需求文档中的公式逐字验证。如果公式包含累加组件（存量+增量），则不能从零开始 |
| **关联规则** | 睡眠户唤醒 v2.8.1 |

### 案例#006 | 类别: 数据不一致 — 唤醒列与明细列不对齐（幽灵唤醒）

| 项目 | 内容 |
|------|------|
| **发生版本** | 睡眠户唤醒 v2.5.0~v2.8.1（全系列） |
| **错误场景** | 唤醒判定使用了 DWS_CUST_ASSE_LIAB.INSUR_BAL 进行三产品对比，但目标表 ADS_CUST_SLEEP_WAKE_DTL 只有 DEPO_CURNT_DEPO_BAL、FIXD_DEPO_BAL、FIN_AMT 三列，缺失 INSUR_AMT |
| **具体表现** | 客户因购买保险被标记 WAKE_STATE='1'，但明细表中看不到任何产品余额>0（三种余额均为0），造成"幽灵唤醒"——状态与明细数据矛盾 |
| **根因** | 唤醒判定逻辑和 DTL 表结构设计不同步。开发者在添加 INSUR_BAL 到唤醒判定时，未检视目标表是否具备对应的存储列。写逻辑时关注了 SELECT，但忘了目标端是否需要存储 |
| **改进措施** | **判定逻辑使用的每个数据列，必须在目标表中有对应的存储列。** 新增判定条件前，执行"输入→输出列映射检查"：列出判定使用的所有字段，逐一核对是否在目标表 DDL 中存在 |
| **检测方法** | `判定使用的DWS字段集合 ⊆ 目标表DDL列集合 ?` |
| **关联规则** | 睡眠户唤醒 v2.9.0 |

### 案例#007 | 类别: 文档过期 — 记忆卡片与实际代码严重不一致

| 项目 | 内容 |
|------|------|
| **发生版本** | 睡眠户唤醒 v2.8.0~v2.8.1 期间 |
| **错误场景** | 代码经多次迭代后（移除 SLEEP_TYP/WAKE_DATE、改变唤醒定义），记忆卡片仍保留旧字段描述、旧版本号、绝对值唤醒定义 |
| **具体表现** | 卡片显示 SLEEP_TYP/WAKE_DATE 存在（已删除）；卡片显示唤醒="持有产品即唤醒"（实际为增量对比）；卡片显示 SP 版本 v2.6.1（实际 v2.8.1） |
| **根因** | 每次代码变更后未同步更新记忆卡片。变更节奏快 → 文档滞后 → 认知错位 |
| **改进措施** | 记忆卡片更新必须作为**代码变更的同一批次**提交，不得分两次。版本号、DDL 字段描述、指标定义、SP 版本——四个维度必须全部同步 |
| **关联规则** | 16.2.2.1 记忆卡片版本控制规则 |

### 案例#008 | 类别: 代码质量 — 注释与代码行为矛盾

| 项目 | 内容 |
|------|------|
| **发生版本** | 睡眠户唤醒 v2.8.1 |
| **错误场景** | L64-66 注释写"月首日：不读取昨日DTL(跨月不沿用)"，但 v2.8.1 已改为每天读取 |
| **具体表现** | 阅读代码的人会被注释误导，认为月首日跳过读取 |
| **根因** | 修改逻辑时只改了代码，忘记同步更新上方注释 |
| **改进措施** | 逻辑变更时必须核对该逻辑块的所有注释，确保注释描述的语义与代码行为一致。遵循"改逻辑→找注释→改注释"三连操作 |
| **关联规则** | 16.3.2 修改后验证 |

### 案例#009 | 类别: 代码质量 — 冗余 JOIN（无引用列）

| 项目 | 内容 |
|------|------|
| **发生版本** | 睡眠户唤醒 v2.6.1~v2.6.2 |
| **错误场景** | 步骤[E]中 `JOIN DWD_CUST_INDV_INFO c` 的 SELECT 列表和 WHERE 条件中均未引用 c 的任何列 |
| **具体表现** | 每次 UPDATE 触发一次无意义的 DWD_CUST_INDV_INFO 全表扫描，纯性能浪费 |
| **根因** | CTE 转 TMP 表时遗留的冗余关联，重构后未做 JOIN 引用检查 |
| **改进措施** | 代码重构后，逐条验证每个 JOIN 是否在 SELECT/WHERE 中有实际引用列。无引用的 JOIN 一律删除 |
| **关联规则** | 睡眠户唤醒 v2.7.0 |

### 案例#010 | 类别: 流程违规 — 未获确认即开始执行

| 项目 | 内容 |
|------|------|
| **发生版本** | 睡眠户唤醒 v2.9.0 |
| **错误场景** | 用户"确认开始修复"前，在尚未获批准的审核确认点阶段就开始修改 DDL 文件 |
| **具体表现** | 用户指出"我没有确认让你执行的时候不能默认执行" |
| **根因** | 将"设计方案已写好"等同于"用户可以开始执行"，未等待用户明确说"开始"/"执行" |
| **改进措施** | 设计方案输出后，必须等待用户明确的执行指令（如"确认，开始修复"/"执行"）。不可因方案已详尽而默认进入编码。方案 → 审批 → 执行的边界不可逾越 |
| **关联规则** | 16.3.1 修改前确认 |
