# 全局不变量（Invariants）

> 层级：L0 CORE
> 版本：v1.0
> 加载策略：会话启动必载；其它文档只引用编号，禁止复述全文

违反任一条必须停止当前写操作，标记阻塞并请求用户决策。

## I-01 禁止猜测

任何字段、表、规则、类型、别名、转换、来源不确定时，必须标记为 `【待确认】` 或 `unresolved`。禁止用猜测补齐。

## I-02 用户命令驱动

禁止擅自生成/修改数据资产、禁止擅自 git commit/push、禁止擅自修复循环。只读分析与只读校验可在授权范围内执行。

## I-03 修改前确认

所有修改前必须说明操作内容、影响范围与风险，并获得用户明确确认。设计完成 ≠ 授权执行。

## I-04 变更白名单

涉及数据资产的写操作前，必须有经用户确认的变更范围（`change_manifest` 或等价白名单）。执行器只能修改清单内路径与目标表。

## I-05 可追溯

所有可修改内容必须能追溯到需求、数据字典或 Mapping。表结构以 Mapping Excel 为最高优先级权威源；Excel 与 MD/DD/DDL 冲突时以 Excel 为准，且字段增删改名仍须用户确认。

## I-06 日期参数

业务相对日期必须使用具名变量 + `sys_fun_deal_date(V_SYSDAT, n)`。禁止用 `TO_DATE` / `TRUNC` / `ADD_MONTHS` 等从 `V_SYSDAT` 直接推导业务边界。细则见 `governance/stored_procedure_date_parameter_rules.md`。

## I-07 SQL 底线

- 禁止 `SELECT *`
- 必须显式字段与表别名
- `UPDATE` / `DELETE` 必须带 `WHERE`
- 目标表日期输出格式 `YYYYMMDD`（存储过程场景）

## I-08 记忆卡片

存在规则记忆卡片时，开发前必须比对版本；不一致须列出差异并经用户确认。代码变更与卡片版本/映射须同批次维护。

## I-09 阶段门禁

未创建任务清单、范围未确认、校验失败、验收未完成时，不得进入下一阶段。不得将"上下文过长/复杂"作为结束条件。

## I-10 Git 边界

仅在 `master` 工作；不创建或切换分支。提交与推送必须在用户明确授权且门禁通过后执行。

## I-11 流程互斥

一次只执行一个写流程 profile：`requirement_development` 或 `schema_change`。二者信号同时存在时先需求开发，再表结构变更；无法唯一路由时停止并澄清。

## I-12 输出合同

AI 输出遵守 `docs/core/output_contract.md`。禁止每轮强制输出完整 8 段长模板。
