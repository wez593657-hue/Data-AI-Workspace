# 产品推荐规则 v2.0

## 1. 文档说明

### 1.1 文档目的

本文档用于定义零售 CRM 产品推荐的业务规则、评分口径、数据要求和技术实现边界，作为产品推荐服务、产品推荐页面、推荐历史和营销触达功能的统一规则依据。

### 1.2 适用范围

产品推荐适用于客户 360 视图中的统一产品推荐列表，覆盖以下产品类别：

- 存款；
- 理财；
- 贷款；
- 保险。

最终仍输出一个统一推荐列表，不按产品类别拆分展示，不设置贷款或保险的保底数量。

### 1.3 版本原则

本版本基于当前产品管理模块已有字段设计。贷款和保险推荐只能使用当前已存在的结构化字段，不使用尚未在产品管理模块维护的贷款用途、额度区间、保障责任、保额等字段进行自动判断。

## 2. 总体方案

### 2.1 推荐流程

```text
全量产品池
    -> 公共硬过滤
    -> 按产品类别路由
       -> 存款/理财规则
       -> 贷款规则
       -> 保险规则
    -> 类别内评分（0~100）
    -> 合并候选产品
    -> 统一排序
    -> 输出 Top 3，最多展示 5 个
```

### 2.2 核心原则

1. 产品推荐采用“分类计算、统一排序”。
2. 各产品类别使用独立的准入和评分逻辑。
3. 各类别评分结果统一转换为 0～100 分后直接比较。
4. 不设置类别配额，不要求推荐结果必须包含某一产品类别。
5. 贷款推荐不代表授信审批通过。
6. 保险推荐不代表具体保障匹配、健康告知通过或最终承保。
7. 客户范围为优质及以上客户。
8. 推荐结果必须保留规则版本、数据截止时间和命中理由，支持审计追溯。

### 2.3 统一评分公式

```text
类别评分 = Σ（评分维度得分 × 维度权重）
最终匹配度 = ROUND(类别评分, 2)
```

所有评分维度均为 0～100 分，类别内各维度权重合计 100%。

## 3. 数据时间口径

1. 推荐计算时点记为 `T`。
2. 客户资产、负债、风险、保单和信贷数据必须记录数据截止日期 `data_as_of`。
3. 推荐不得使用晚于推荐计算时点的未来数据。
4. 上游 T-1 数据未到达时，沿用最近一个有效数据快照，并标记数据日期。
5. 产品销售状态以推荐计算时点 `T` 的有效状态为准。
6. 客户历史购买记录的时间窗口：
   - 存款/理财期限偏好：近36个月；
   - 存款/理财历史熟悉度：近 12 个月；
   - 贷款显性需求：按不同事件保留 90～180 天；
   - 保险保单有效性：以 `T` 时点保单状态和保障期间为准。

## 4. 统一数据对象

### 4.1 推荐结果字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| customer_id | String | 客户唯一标识 |
| product_id | String | 产品唯一标识 |
| product_category | Enum | 存款、理财、贷款、保险 |
| score | Decimal(5,2) | 最终匹配度，范围 0～100 |
| trigger_type | Enum | 到期承接、显性意向、潜在需求、保障缺口 |
| reason_codes | Array | 推荐理由编码 |
| recommendation_confidence | Enum | HIGH、MEDIUM、LOW |
| data_completeness | Decimal(5,2) | 客户和产品数据完整度 |
| calculated_at | DateTime | 评分计算时间 |
| data_as_of | DateTime | 使用的数据截止时间 |
| rule_version | String | 规则版本，例如 v2.0 |

### 4.2 公共产品字段

公共字段至少包括：

- 产品编号；
- 产品名称；
- 产品类别；
- 产品状态；
- 当前销售渠道可售状态。

## 5. 公共硬过滤规则

以下任一条件不满足，产品直接从候选池剔除：

1. 产品状态不是在售。
2. 产品被业务配置为禁止推荐。
3. 产品编号、产品名称或产品类别为空。
4. 产品已经超过募集期、认购期或销售有效期。
5. 产品类别无法映射到存款、理财、贷款、保险四类之一。

公共过滤完成后，按照产品类别路由到对应的评分规则。

## 6. 存款/理财推荐规则

存款和理财沿用原产品推荐方案的“风险适配、产品可售硬过滤 + 四维评分”模型。

### 6.1 硬过滤

#### 6.1.1 风险适配

客户风险承受等级使用 `C1～C5`，产品风险等级使用 `R1～R5`。

```text
产品风险等级 > 客户风险承受等级：直接剔除
```

#### 6.1.2 产品可售

产品必须同时满足：

- 产品状态为在售；
- 产品未过认购、募集或销售截止时间。

### 6.2 评分模型

| 评分维度 | 权重 |
| --- | ---: |
| 收益吸引力 | 35% |
| 期限匹配度 | 30% |
| 风险舒适度 | 20% |
| 历史偏好/熟悉度 | 15% |

### 6.3 收益吸引力：35%

#### 6.3.1 可比产品分组

建议按照以下字段分组：

```text
产品类别 + 产品子类型 + 风险等级 + 币种 + 期限区间
```

收益字段按产品类型取值：

- 普通定期：产品利率；
- 自营理财：业绩比较基准或有效收益率；
- 代销理财：统一口径的近期年化收益率；
- 无有效收益字段：使用中性分 60 分。

#### 6.3.2 评分

| 同类产品收益排名 | 得分 |
| --- | ---: |
| 前 10% | 100 |
| 10%～30% | 80 |
| 30%～50% | 60 |
| 50%～80% | 30 |
| 后 20% | 0 |
| 无足够可比样本或收益字段缺失 | 60 |

同收益率时按产品编号升序作为稳定排序。

### 6.4 期限匹配度：30%

1. 统计客户近 36 个月的有效购买记录。
2. 排除撤销、失败、冲正和购买金额为 0 的记录。
3. 产品期限统一换算为月数。
4. 以购买金额最大的期限区间作为客户主要期限偏好。

| 产品期限与主要期限偏差 | 得分 |
| --- | ---: |
| 落入主要期限区间 | 100 |
| 偏差小于等于 3 个月 | 80 |
| 大于 3 个月且小于等于 6 个月 | 60 |
| 大于 6 个月且小于等于 12 个月 | 30 |
| 大于 12 个月 | 0 |
| 客户无历史数据或产品期限不适用 | 60 |

期限为区间时，只要产品期限与客户偏好区间存在交集，即视为命中。

### 6.5 风险舒适度：20%

产品风险等级不得高于客户风险承受等级。通过硬过滤后，按差值评分：

| 产品风险等级与客户上限差值 | 得分 |
| --- | ---: |
| 相同 | 100 |
| 低 1 档 | 90 |
| 低 2 档 | 80 |
| 低 3 档 | 70 |
| 低 4 档及以上 | 60 |

### 6.6 历史偏好/熟悉度：15%

检查以下三个命中项：

1. 产品类型是否为客户近 12 个月购买频次最高的大类。
2. 发行机构是否为客户近 12 个月购买频次最高的机构。
3. 客户近 12 个月是否购买过同类产品。

| 命中情况 | 得分 |
| --- | ---: |
| 三项全部命中 | 100 |
| 命中两项且包含产品类型 | 80 |
| 命中两项但不包含产品类型 | 60 |
| 仅命中一项 | 30 |
| 三项均未命中 | 0 |

## 7. 贷款推荐规则

### 7.1 规则边界

当前产品管理模块中贷款产品已明确的字段主要包括：

- 产品名称；
- 产品编号；
- 产品类型，例如经营贷、消费贷；
- 最低利率定价。

当前未形成结构化字段的贷款用途、贷款金额区间、贷款期限、还款方式、年龄限制、职业限制和区域限制，不作为自动化精确匹配条件。

### 7.2 贷款候选触发

#### 7.2.1 显性需求直接进入

以下任一条件满足，即进入贷款候选池：

| 触发条件 | 有效期 |
| --- | ---: |
| 潜客意向产品包含个人贷款 | 180 天 |
| 存在贷款转介记录 | 180 天 |
| 营销反馈选择个人贷款 | 90 天 |
|  |
|  |

#### 7.2.2 潜在需求触发

潜在需求必须同时满足：

- 至少命中 2 个正向融资信号；
- 潜在需求总分达到 60 分；
- 不存在严重逾期、不良、免打扰情况；
- 客户KYC有可核验的收入、资产、流水或授信信息；
- 不存在明显的同类贷款重复推荐风险。

| 客户侧融资信号 | 分值 |
| --- | ---: |
| 存在明确消费、经营、购房或资金周转场景 | 35 |
| 有效授信额度不足或存在融资缺口 | 30 |
| 有稳定收入、代发或经营流水 | 20 |
| 有正常还款历史或既有信贷关系 | 15 |

### 7.3 贷款硬过滤

1. 产品状态为在售。
2. 产品编号、产品类型和产品对象不为空。
3. 客户未命中严重逾期、不良、免打扰情况。
5. 已持有同一产品时，只有存在续贷、增额或置换意向才允许再次推荐。
6. 产品类型无法识别或产品对象无法映射时，不进入候选池。

以下字段当前不作为自动硬过滤条件：贷款用途、贷款金额、贷款期限、还款方式、区域限制、年龄限制、职业限制和担保方式实际可行性。

### 7.4 贷款评分模型

| 评分维度 | 权重 |
| --- | ---: |
| 融资需求强度 | 50% |
| 产品类型与客户对象匹配度 | 30% |
| 客户信贷关系与转化基础 | 10% |
| 最低利率定价竞争力 | 10% |

### 7.5 融资需求强度：50%

| 需求来源 | 基准分 |
| --- | ---: |
| 已提交贷款申请 | 100 |
| 有效贷款转介 | 95 |
| 客户明确表达贷款意向 | 90 |
| 营销反馈选择贷款 | 80 |
| 客户经理创建贷款任务 | 75 |
| 潜在融资需求 | 60～75 |

时间衰减：

| 事件距当前时间 | 衰减系数 |
| --- | ---: |
| 0～7 天 | 1.00 |
| 8～30 天 | 0.90 |
| 31～90 天 | 0.75 |
| 91～180 天 | 0.60 |

```text
融资需求强度 = 最高有效需求基准分 × 时间衰减系数
```

多个事件同时存在时取最高有效分，不重复累加。

### 7.6 产品类型与客户对象匹配度：30%

当前仅基于产品类型和产品对象判断：

| 匹配情况 | 得分 |
| --- | ---: |
| 产品类型与客户明确贷款方向一致，且产品对象匹配 | 100 |
| 产品类型与贷款方向一致，但产品对象信息不完整 | 80 |
| 仅产品对象匹配，贷款方向不明确 | 60 |
| 产品类型或产品对象无法确认 | 50 |
| 产品对象明确不匹配 | 0，剔除 |

建议配置贷款产品类型映射：

| 产品类型 | 客户侧可映射场景 |
| --- | --- |
| 经营贷 | 经营、企业主、个体经营者 |
| 消费贷 | 个人消费、工薪客户 |
| 按揭贷 | 购房、住房按揭 |

映射表作为规则参数维护，不要求新增产品字段。

### 7.7 客户信贷关系与转化基础：10%

| 客户情况 | 得分 |
| --- | ---: |
| 有正常同类贷款且存在续贷/增额需求 | 100 |
| 有其他正常贷款或授信关系 | 80 |
| 有代发、结算或经营流水关系 | 60 |
| 无信贷历史但有显性需求 | 50 |
| 信贷数据缺失 | 40 |
| 存在不良或严重逾期 | 直接过滤 |

### 7.8 最低利率定价竞争力：10%

在同一产品类型和客户对象候选集内，按最低利率定价升序排名：

| 排名 | 得分 |
| --- | ---: |
| 前 10% | 100 |
| 10%～30% | 80 |
| 30%～50% | 60 |
| 50%～80% | 30 |
| 后 20% | 0 |
| 无最低利率定价 | 50 |

最低利率定价仅用于同类产品内部排序，不代表客户实际执行利率。

贷款推荐理由必须包含：

> 该推荐仅表示初步营销匹配，实际贷款金额、期限、担保方式和利率以信贷系统及授信审批结果为准。

## 8. 保险推荐规则

### 8.1 规则边界

当前产品管理模块中保险产品已明确的字段主要包括：

- 险种分类；
- 保险公司；
- 风险等级；
- 保障期间；
- 起购金额；
- 缴费方式；
- 缴费期限；
- 是否在售。

当前未形成结构化字段的保障责任、保额、目标客群、年龄限制、职业限制、健康告知和具体核保规则，不作为 CRM 自动化精确判断条件。

### 8.2 保险推荐触发

保险只以保障缺口代理判断为核心触发，不因收益率或到期承接直接推荐。

#### 8.2.1 险种分类缺口

以下任一情况成立，视为存在该险种的基础保障缺口：

- 客户有效保单中不存在该险种分类；
- 同类保单已失效；
- 同类保单已退保；
- 同类保单在 180 天内到期；
- 同类保单待生效且无法形成当前有效保障。

#### 8.2.2 生命周期缺口

结合客户年龄、家庭关系、收入和贷款余额等已有客户信息，判断客户是否处于以下阶段：

- 成年保障阶段；
- 婚姻及家庭责任阶段；
- 子女抚养阶段；
- 退休准备阶段。

由于产品缺少具体保障责任字段，生命周期判断只能用于险种分类级推荐，不能证明具体产品责任覆盖客户风险。

### 8.3 保险硬过滤

1. 产品状态为在售且当前渠道可售。
2. 险种分类、保险公司、保障期间等核心字段不为空。
3. 险种分类可以映射到已配置的保障类别。
4. 客户不存在有效同类保单，或同类保单已到期/即将到期。
5. 产品风险等级高于客户可承受等级时直接剔除。
6. 产品基本适用性字段缺失且无法完成最低适配校验时，不进入候选池。

以下字段当前不作为自动过滤条件：保障责任、保额、目标人群、年龄/职业限制、健康告知、核保结论和具体地区销售限制。

### 8.4 保险评分模型

| 评分维度 | 权重 |
| --- | ---: |
| 险种分类缺口匹配度 | 45% |
| 生命周期与家庭责任匹配度 | 20% |
| 缴费负担与缴费方式适配度 | 15% |
| 保障期间匹配度 | 10% |
| 产品及客户数据完整度 | 10% |

### 8.5 险种分类缺口匹配度：45%

| 客户与险种分类关系 | 得分 |
| --- | ---: |
| 客户无有效同类保单 | 100 |
| 同类保单 180 天内到期 | 80 |
| 同类保单已失效或待生效 | 70 |
| 已有同类有效保单且无续保需求 | 0，剔除 |
| 保单数据缺失 | 50 |

该评分表示险种类别存在缺口，不表示具体产品责任已覆盖客户实际风险。

### 8.6 生命周期与家庭责任匹配度：20%

| 客户侧情况 | 得分 |
| --- | ---: |
| 年龄、家庭责任和险种类别均匹配 | 100 |
| 年龄或家庭责任至少一项匹配 | 80 |
| 仅有一般生命周期信号 | 60 |
| 家庭信息不完整 | 50 |
| 无法判断 | 40 |

建议的险种分类映射：

| 险种分类 | 可关联客户信号 |
| --- | --- |
| 意外类 | 年龄、职业、出行或家庭责任 |
| 医疗类 | 年龄、家庭成员、已有医疗保障 |
| 重疾类 | 年龄、家庭责任、已有重疾保障 |
| 寿险类 | 配偶、子女、父母、贷款余额 |
| 养老类 | 年龄、退休阶段、养老准备情况 |

### 8.7 缴费负担与缴费方式适配度：15%

如果客户存在年稳定收入，按以下公式计算：

```text
最低年化缴费负担率
= 起购金额 × 年缴费次数 / 年稳定收入
```

| 年化缴费负担率 | 得分 |
| --- | ---: |
| 小于等于 5% | 100 |
| 5%～8% | 80 |
| 8%～12% | 60 |
| 12%～20% | 30 |
| 大于 20% | 0，原则上不推荐 |

缴费方式匹配：

| 客户情况与产品缴费方式 | 得分 |
| --- | ---: |
| 稳定收入且期交产品 | 100 |
| 有一次性资金且趸交产品 | 100 |
| 客户收入特征与缴费方式基本匹配 | 80 |
| 客户缴费能力不明确 | 50 |
| 明显不匹配 | 30 |

如果产品只有起购金额，没有可计算的年缴费金额，则本维度取 50 分，并增加数据不足提示。

### 8.8 保障期间匹配度：10%

仅基于产品保障期间和客户当前生命周期判断：

| 匹配情况 | 得分 |
| --- | ---: |
| 保障期间与客户当前责任阶段高度匹配 | 100 |
| 基本匹配 | 80 |
| 客户无明确期限偏好 | 60 |
| 保障期间明显不适合当前阶段 | 30 |
| 保障期间缺失 | 50 |

不得根据保障期间推断具体保额是否足够。

### 8.9 产品及客户数据完整度：10%

```text
数据完整度得分
= 产品字段完整度 × 50% + 客户字段完整度 × 50%
```

产品侧字段：险种分类、保险公司、风险等级、保障期间、起购金额、缴费方式、缴费期限、在售状态。

客户侧字段：年龄、家庭关系、收入、已有保单、保单状态、保单起止日期和客户风险偏好。

缺少年龄、地区等产品最低适用性字段时，执行硬过滤；缺少家庭责任、收入或保额等保障缺口字段时，允许推荐但降低评分。

保险推荐结果增加：

```text
recommendation_level = CATEGORY_LEVEL_ONLY
```

推荐理由必须包含：

> 当前推荐基于险种分类和客户已有保单情况；因产品保障责任及保额字段未结构化，结果仅供初步营销参考。

## 9. 统一合并排序

### 9.1 合并规则

各类别完成独立评分后合并候选集：

```text
候选产品 = 存款/理财候选 + 贷款候选 + 保险候选
```

不设置贷款或保险的最低数量、最高数量和类别保底。

### 9.2 排序规则

按以下字段依次降序/升序排序：

1. `score` 最终匹配度降序；
2. 显性需求优先于到期承接、保障缺口和潜在需求；
3. 类别主维度得分降序；
4. `data_completeness` 数据完整度降序；
5. 产品编号升序。

同分排序中的触发类型只作为稳定排序兜底，不改变完全按统一总分排序的总体原则。

### 9.3 输出数量

- 候选产品大于等于 3 个：默认输出前 3 个；
- 候选产品为 1～2 个：全部输出；
- 候选产品为空：提示“暂无适配产品”；
- 页面最多支持继续查看 5 个推荐产品。

## 10. 推荐理由规则

### 10.1 理由编码

| 类别 | 推荐理由编码 |
| --- | --- |
| 存款/理财 | `RISK_MATCH`、`TERM_MATCH`、`YIELD_TOP`、`HISTORY_MATCH` |
| 贷款 | `LOAN_INTENT`、`LOAN_SCENARIO`、`CUSTOMER_OBJECT_MATCH`、`CREDIT_RELATION`、`RATE_COMPETITIVE` |
| 保险 | `COVERAGE_CATEGORY_GAP`、`LIFE_STAGE_MATCH`、`POLICY_GAP`、`PREMIUM_FIT`、`DATA_PARTIAL` |

### 10.2 文案生成

推荐理由由“最多两个正向命中理由 + 必要的限制提示”组成。

贷款示例：

> 该产品匹配客户的个人贷款意向，产品类型和客户对象基本匹配，当前最低利率定价在同类产品中具有竞争力。推荐结果不代表授信审批通过。

保险示例：

> 该险种可补充客户当前同类保障缺口，与客户生命周期阶段基本匹配。因产品保障责任及保额字段未结构化，结果仅供初步营销参考。

存款/理财示例：

> 该产品风险等级符合客户风险承受能力，期限与客户历史偏好匹配，在同类产品中收益表现较优。

## 11. 权限与展示约束

1. 客户概览和移动端产品推荐页面可展示统一推荐结果。
2. PC 端客户概览中，管户客户经理和其他有客户查看权限的用户可查看推荐产品。
3. 到期承接推荐和推荐历史遵循客户 360 视图已有权限规则。
4. 推荐产品点击后进入产品详情页面。
5. 移动端支持将产品分享至企业微信。
6. 产品营销话术、产品封面、PC 端海报和移动端海报由产品管理模块维护。

## 12. 置信度规则

| 置信度 | 判断条件 |
| --- | --- |
| HIGH | 产品和客户关键字段完整，且主要评分维度均可计算 |
| MEDIUM | 部分客户数据缺失，但仍满足主要推荐条件 |
| LOW | 贷款缺少产品细分字段，或保险只能按险种分类判断 |

贷款和保险默认不因置信度低而自动剔除，但必须在推荐理由中显示限制说明；只有公共硬过滤或类别硬过滤不通过时才剔除。

## 13. 当前明确不支持的自动判断

由于产品管理模块暂未提供结构化字段，以下规则不得在 v2.0 中作为自动化判断：

### 13.1 贷款

- 贷款用途与产品用途精确匹配；
- 贷款金额区间匹配；
- 贷款期限匹配；
- 还款方式匹配；
- 区域、年龄、职业限制校验；
- 担保方式实际可行性判断；
- 授信审批结论预测。

### 13.2 保险

- 保障责任覆盖率；
- 保额缺口比例；
- 具体责任重复保障判断；
- 目标人群精确匹配；
- 健康告知结论；
- 核保或承保结论；
- 具体地区销售限制判断。

## 14. 技术实现建议

### 14.1 服务拆分

建议拆分为以下能力：

1. 公共产品过滤服务；
2. 存款/理财评分服务；
3. 贷款触发与评分服务；
4. 保险缺口代理与评分服务；
5. 推荐结果合并排序服务；
6. 推荐理由生成服务；
7. 推荐历史记录服务。

### 14.2 规则参数化

以下内容必须配置化：

- 产品类型和客户场景映射；
- 贷款显性需求有效期；
- 潜在融资信号分值；
- 保险险种分类映射；
- 保障缺口代理阈值；
- 年化缴费负担率阈值；
- 各评分维度权重；
- 推荐理由文案和限制提示。

### 14.3 规则版本

每次规则调整需生成新的 `rule_version`，推荐历史保存计算时使用的规则版本，历史结果不因新规则重新覆盖。

## 15. 待业务确认参数

以下参数需要信贷、保险及零售业务确认后才能正式投产：

1. 贷款潜在需求信号及其分值；
2. 严重逾期、不良和禁止营销状态清单；
3. 贷款产品类型与客户场景映射表；
4. 保险险种分类与生命周期信号映射表；
5. 保险起购金额到年化缴费金额的换算规则；
6. 保险保障期间与生命周期的匹配口径；
7. 客户收入、家庭关系和保单数据的有效性标准；
8. 贷款和保险数据缺失时的具体默认分值；
9. 产品推荐默认 Top N 和最多展示数量；
10. 推荐理由文案及合规提示。

## 16. 结论

v2.0 采用“分类路由、独立评分、统一排序”的产品推荐模型：

- 存款/理财继续使用成熟的收益、期限、风险和历史偏好模型；
- 贷款基于融资意向、客户对象、信贷关系和最低利率定价进行初步营销推荐；
- 保险基于险种分类缺口、生命周期、已有保单和缴费基础信息进行类别级推荐；
- 贷款和保险不使用当前产品管理模块不存在的字段进行虚假精确匹配；
- 所有推荐结果保留评分、理由、数据完整度、置信度和规则版本，支持统一展示和审计追溯。
