## 三、详细分析

### F-01 [严重] — 2.2 INSERT 和 2.3 UPDATE 段落缺失

**位置**: [PRC_DWD_ACCT_INSUR.sql](file:///d:/AI/AI-Workspace/Kingbase-CRM-AI-Development-Guide/data_assets/stored_procedure/ods_to_dwd/PRC_DWD_ACCT_INSUR.sql) L241 之后

**现象**: SP头部注释声明了4段处理流程：

```sql
-- 2.1 生成保单级主档聚合快照（一次计算，供后续段落复用）
-- 2.2 新增逻辑：快照主键在目标表中【不存在】时批量 INSERT
-- 2.3 更新逻辑：主键【已存在】时批量 UPDATE（刷新状态/余额/日期/机构）
-- 2.4 统一提交（新增+更新同一事务，失败整体回滚）
```

但实际代码在 2.1 的 `COMMIT`（L241）和 `SYS_PRC_STEP_LOGS`（L248）之后直接进入 `EXCEPTION`（L253），**2.2/2.3/2.4 段落完全缺失**。

**影响**: 
- 快照数据写入 `TMP_DWD_ACCT_INSUR_SNAP` 临时表后从未转移到目标表 `DWD_ACCT_INSUR`
- 所有下游SP读取 `DWD_ACCT_INSUR` 时将得到**空表或过期数据**
- CUMU、SLEEP_WAKE、DEADLINE_RMND 等全部受影响

**推断原因**: v2.3.0 在 v2.2.0 基础上修改 TX_DATE/LAST_TX_DATE 来源时，2.2/2.3 段落被意外截断。

**修复**: 需补充 MERGE/UPSERT 逻辑（基于四键主键 `CUST_ID, ACCT_ID, PRDKT_ID, INSUR_BID_FORM_NO` 执行 INSERT ON CONFLICT 或分开的 INSERT/UPDATE）。


### F-02 [严重] — INSUR_PERIOD_TYP 与 PAY_PERIOD_TYP 字段互换

**位置**: [PRC_DWD_ACCT_INSUR.sql L191-194](file:///d:/AI/AI-Workspace/Kingbase-CRM-AI-Development-Guide/data_assets/stored_procedure/ods_to_dwd/PRC_DWD_ACCT_INSUR.sql#L191-L194)

**当前代码**:
```sql
d.PAY_PER_UNIT    AS INSUR_PERIOD_TYP,   -- 错：PAY(缴费)周期→保险期间类型
d.PAY_PER_NUM     AS INSUR_PERIOD,       -- 错：PAY(缴费)数量→保险期间值
d.VALID_PER_UNIT  AS PAY_PERIOD_TYP,     -- 错：VALID(保险)周期→缴费期间类型
d.VALID_PER_NUM   AS PAY_PERIOD,         -- 错：VALID(保险)数量→缴费期间值
```

**ODS源表语义** (`YBT_YBT_POLICY_INSURANCE_INFO`):
| 源字段 | 含义 |
|--------|------|
| `pay_per_unit` | 期缴缴费周期计算单位（12=年, 1=月, 2=日, 0=至某年龄, -1=终生） |
| `pay_per_num` | 期缴缴费周期计算数量 |
| `valid_per_unit` | **保险周期**计算单位（12=年, 1=月, 2=日, 0=至某年龄, -1=终身） |
| `valid_per_num` | **保险周期**计算数量 |

**正确映射应为**:
```sql
d.VALID_PER_UNIT  AS INSUR_PERIOD_TYP,   -- 保险期间类型 ← 保险周期单位
d.VALID_PER_NUM   AS INSUR_PERIOD,       -- 保险期间值   ← 保险周期数量
d.PAY_PER_UNIT    AS PAY_PERIOD_TYP,     -- 缴费期间类型 ← 缴费周期单位
d.PAY_PER_NUM     AS PAY_PERIOD,         -- 缴费期间值   ← 缴费周期数量
```

**影响**: 所有依赖 INSUR_PERIOD_TYP/PAY_PERIOD_TYP 的下游逻辑将使用错误的周期信息。

**佐证**: CANCL_INSUR_DATE 计算（L164-176）使用 `d.VALID_PER_UNIT`（保险期间），PAY_UPTO_DATE 计算（L177-190）使用 `d.PAY_PER_UNIT`（缴费期间）——业务计算本身是正确的，只是存入的**列名互换了**。

### F-05 [中] — 60天宽限期逻辑使用全局COUNT而非最近一笔

**位置**: [PRC_DWD_ACCT_INSUR.sql L131-139](file:///d:/AI/AI-Workspace/Kingbase-CRM-AI-Development-Guide/data_assets/stored_procedure/ods_to_dwd/PRC_DWD_ACCT_INSUR.sql#L131-L139)

**当前逻辑**:
```sql
WHEN P.PAY_PATRN = '1'
 AND P.PAY_PERIOD_TYP IN ('12','1','2')
 AND V_DATA_DATE > CASE P.PAY_PERIOD_TYP
        WHEN '12' THEN ADD_MONTHS(MIN(P.ACCEPT_DATE_PARSED),
                    (1 + COUNT(CASE WHEN P.TRAN_TYPE = '1' THEN 1 END)) * 12) + 60
        ...
    END
THEN 0  -- 60天宽限期已过且未缴
```

`COUNT(CASE WHEN P.TRAN_TYPE = '1' THEN 1 END)` 统计**所有**续期记录数（基于 GROUP BY 范围），而非最近一笔续期的序号。

**场景示例**: 一份按年缴的保单，已缴费5期（每年1期），第1期在1年前缴、第5期在1个月前缴。`COUNT(续期)=5`，窗口上界 = 投保日 + 6×12个月 + 60天 ≈ 投保日后6年2个月。实际上第5期缴费后只需再过6个多月就进入宽限期，但现在窗口被拉到了6年后，**INSUR_AMT永远不会被清零**。

**正确逻辑**: 应取 `MAX(ORD_CREATE_DATE)` 作为最近续期日期，或计算 `MAX(续期序号)`。
