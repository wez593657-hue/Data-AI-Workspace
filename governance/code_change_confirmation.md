# 代码变更确认机制

> 生效日期：2026-08-03
> 适用范围：本仓库内所有数据资产代码文件（存储过程、DDL、TMP 表、映射、需求与校验脚本）的修改。

## 一、目的

确保所有代码修改在**人工审核确认通过后**方可执行，杜绝未确认的代码写入；
同时强制满足以下三条架构约束，保证明细/统计处理逻辑的单一性与两期数据处理的清晰分离。

## 二、强制架构约束

| 编号 | 约束 | 说明 |
|---|---|---|
| C1 | 明细处理逻辑单过程化 | 明细数据处理逻辑必须完全包含在**单个存储过程** `PRC_ADS_CUST_DEADLINE_RMND_DTL` 内实现，不得拆分至多个存储过程（允许过程内部嵌套模块） |
| C2 | 统计处理逻辑单过程化 | 统计数据处理逻辑必须完全包含在**单个存储过程** `PRC_ADS_CUST_DEADLINE_RMND_STATIS` 内实现，不得拆分至多个存储过程（允许过程内部嵌套模块） |
| C3 | 两期逻辑段落分离 | 本期数据与上期数据必须在代码中通过**明确的逻辑段落**分离（同一匿名块内分段落、独立隔离存储表、独立边界检查、独立日志前缀），确保两种数据处理逻辑相互独立、界限清晰 |
| D1 | 禁止嵌套过程 | 存储过程内**不得声明任何嵌套 PROCEDURE/FUNCTION**（含 TRUNC_TMP、日志助手等）；本期与上期逻辑位于**同一个 `BEGIN…END;` 匿名块内**，块内以**注释段落**分隔书写，不拆分为多个独立匿名块 |

## 三、变更确认流程

```
变更提案(DRAFT) → 人工审核(PENDING_REVIEW) → 确认(APPROVED) → 执行(EXECUTED) → 验证(VERIFIED)
```

### 1. 变更提案（AI 提交）

AI 在**任何代码文件写入之前**，必须提交变更确认单，包含：

- 变更编号与目标；
- 需求/口径依据（编号 + 文档出处）；
- 影响文件清单（含新建/修改/删除）；
- 字段清单与逻辑改动点（逐项）；
- 约束符合性自查（C1/C2/C3）；
- 测试与验证计划；
- 风险与回退方案。

### 2. 人工审核（用户执行）

用户核对变更确认单，重点检查：

- 是否满足 C1/C2/C3；
- 是否与已确认口径（业务规则）一致；
- 影响面是否可控、是否存在跨期干扰；
- 测试计划是否覆盖冻结/更新/边界/幂等场景。

### 3. 确认 / 拒绝

- 确认：用户明确回复「确认」（或批准指定变更编号）；
- 拒绝/调整：用户提出修改意见，变更单退回 DRAFT 调整后重新提交。

### 4. 执行与验证

- 仅获确认的变更单允许执行代码写入；
- 执行后必须运行静态校验与测试并回报结果；
- 验证通过后变更单置为 VERIFIED 并归档。

## 四、禁止事项

- 未提交变更确认单或未经 APPROVED 状态，禁止对代码文件执行任何写入（apply_patch、脚本改写等）；
- 禁止将明细/统计处理逻辑拆分为多个顶层存储过程（约束 C1/C2）；
- 禁止在存储过程内声明嵌套过程（约束 D1）；本期与上期逻辑必须位于同一个 `BEGIN…END;` 匿名块内并以注释段落分隔；
- 禁止在本期与上期计算模块之间共享可变中间结果（约束 C3，仅允许共享周期中性输入抽取）。

## 五、变更单归档位置

- 变更确认单：`docs/changes/` 下按日期与变更名命名；
- 已执行变更的实施记录：`docs/changes/` 下既有实施文档命名规范。
